# Verovio SVG Output Patterns

## Basic SVG Structure

Verovio renders each MEI element as an SVG `<g>` group:

```xml
<g id="note-0000001" class="note">
  <!-- child elements: <use>, <path>, <polyline>, <text>, nested <g> -->
</g>
```

- **`id`** corresponds to the MEI `xml:id` attribute (if present) or is auto-generated by Verovio
- **`class`** is the element type name (note, rest, measure, hairpin, etc.)
- Child SVG elements determine which CSS strategy is needed for highlights

## ID Assignment Rules

Verovio assigns `id` attributes to SVG `<g>` elements using these rules:

| MEI source | SVG `id` | Example |
|---|---|---|
| Element with `xml:id` | Exact match of `xml:id` value | `<note xml:id="n1">` → `<g id="n1" class="note">` |
| Element without `xml:id` | Random alphanumeric string | `<staffDef clef.shape="G">` → `<g id="nh5rcn6" class="clef">` |
| Attribute-generated child | Random alphanumeric string | `<note dots="1">` → child `<g id="wz3mrxj" class="dots">` |
| Structural sub-element | Random or no id | `notehead` has no id; `stem` has auto-generated id |

**Key points:**
- Auto-generated IDs are random alphanumeric strings with no consistent prefix or pattern — they cannot be reliably distinguished from user-defined IDs by pattern matching alone
- The editor uses a `validXmlIds: Set<string>` (extracted from MEI source by `getAllXmlIds()`) to filter out auto-generated IDs for interaction purposes
- Only elements whose SVG `id` is in `validXmlIds` respond to hover and click

## Attribute-Generated vs Element-Generated SVG

MEI allows specifying some musical content either as attributes on a parent element or as explicit child elements. Verovio renders both forms visually, but the SVG output differs in ID assignment.

### staffDef attributes → staff-level SVG children

Attributes on `<staffDef>` produce SVG `<g>` elements as direct children of `<g class="staff">`:

```xml
<!-- MEI: attributes on staffDef -->
<staffDef n="1" lines="5" clef.shape="G" clef.line="2" key.sig="2s" meter.count="4" meter.unit="4" />

<!-- SVG output -->
<g class="staff" id="auto-1">
  <g class="clef" id="auto-2">...</g>         <!-- from clef.shape/clef.line -->
  <g class="keySig" id="auto-3">...</g>        <!-- from key.sig -->
    <g class="meterSig" id="auto-4">...</g>    <!-- from meter.count/meter.unit -->
    <g class="layer" id="auto-5">
      ...
    </g>
</g>
```

All IDs are auto-generated. These elements have no `xml:id` in MEI and are not interactive.

### note attributes → note-level SVG children

Attributes on `<note>` produce SVG `<g>` elements as children of the note's `<g>`:

```xml
<!-- MEI: dots and accid as attributes -->
<note xml:id="n1" pname="c" oct="5" dur="4" dots="1" accid="s" />

<!-- SVG output -->
<g class="note" id="n1">              <!-- id = xml:id -->
  <g class="notehead">...</g>         <!-- no id -->
  <g class="dots" id="auto-6">...</g> <!-- auto-generated, from dots attr -->
  <g class="stem" id="auto-7">...</g> <!-- auto-generated, always present -->
  <g class="accid" id="auto-8">...</g><!-- auto-generated, from accid attr -->
</g>
```

### Explicit child elements → user-defined IDs

When the same content is written as explicit MEI child elements with `xml:id`:

```xml
<!-- MEI: accid as explicit child element -->
<note xml:id="n2" pname="d" oct="5" dur="4">
  <accid xml:id="a2" accid="f" />
</note>

<!-- SVG output -->
<g class="note" id="n2">
  <g class="notehead">...</g>
  <g class="stem" id="auto-9">...</g>
  <g class="accid" id="a2">...</g>    <!-- id = xml:id, interactive -->
</g>
```

The `<accid>` now has `id="a2"` matching its `xml:id`, making it individually interactive.

### Common SVG Child Elements

| SVG element | Usage | Colored by |
|-------------|-------|------------|
| `<use>` | Glyph reference (noteheads, accidentals, clefs, etc.) | `fill` |
| `<path>` | Lines, curves, stems | `fill` or `stroke` (depends on context) |
| `<polyline>` | Multi-point lines (hairpin wedges, hooks) | `stroke` |
| `<text>` | Text content (lyrics, dynamics text, etc.) | `fill` |
| `<rect>` | Rectangles (beam lines, barlines) | `fill` |

## CSS Strategy Detection

### How to determine the correct strategy

1. Render an MEI file containing the target element
2. Open DevTools, find the `<g class="ELEMENT_NAME">` group
3. Inspect each child element:

| Child has... | Strategy |
|-------------|----------|
| `<use>` or `<text>` without inline `fill="none"` | **fill** |
| `<path>` / `<polyline>` with inline `fill="none"` | **stroke** |
| Mix of both patterns | **mixed** |

### Key rule

When a child has `fill="none"` set as an **inline attribute**, the default CSS rule (`* { fill: color !important; }`) will override it, causing unwanted interior fills on stroked shapes. This is why stroke-based elements need an explicit override with `fill: none !important; stroke: color !important;`.

## Known Element Patterns

### fill-based (default rules apply)

**note** — Glyph + stem:
```xml
<g id="n1" class="note">
  <g class="notehead">
    <use xlink:href="#E0A4-..." />   <!-- notehead glyph -->
  </g>
  <g class="stem">
    <path d="..." stroke-width="18" />  <!-- stem line, colored by fill -->
  </g>
</g>
```

**dynam / tempo / dir** — Text:
```xml
<g id="d1" class="dynam">
  <text>f</text>   <!-- or <use> for SMuFL glyph dynamics -->
</g>
```

**fermata / breath / caesura** — Single glyph:
```xml
<g id="f1" class="fermata">
  <use xlink:href="#E4C0-..." />   <!-- fermata glyph -->
</g>
```

**trill / mordent / turn / ornam** — Ornament glyph:
```xml
<g id="t1" class="trill">
  <use xlink:href="#E566-..." />   <!-- trill glyph -->
</g>
```
> Note: `<trill>` with extender line may have additional `<path>` children that could require mixed strategy. Not yet verified.

**slur / tie / phrase / lv** — Filled curved path:
```xml
<g id="s1" class="slur">
  <path d="..." />   <!-- filled bezier path, NO inline fill="none" -->
</g>
```
> Verovio renders these as filled shapes, not stroked lines. Default fill rules work. If Verovio changes to stroked rendering, stroke strategy would be needed.

**reh** — Text + enclosure:
```xml
<g id="r1" class="reh">
  <rect ... />          <!-- enclosure box -->
  <text>A</text>        <!-- rehearsal letter -->
</g>
```

**repeatMark** — Segno/coda glyph:
```xml
<g id="rm1" class="repeatMark">
  <use xlink:href="#E047-..." />   <!-- segno/coda glyph -->
</g>
```

**harm / fing** — Text:
```xml
<g id="h1" class="harm">
  <text>V</text>
</g>
```

**bTrem / fTrem** — Note(s) + tremolo slashes:
```xml
<g id="bt1" class="bTrem">
  <g class="note">...</g>          <!-- child note -->
  <path d="..." />                 <!-- tremolo slashes -->
</g>
```

**chord** — Multiple noteheads:
```xml
<g id="c1" class="chord">
  <g class="note">...</g>   <!-- each note in the chord -->
  <g class="note">...</g>
</g>
```

**rest / mRest / beatRpt / halfmRpt / mRpt** — Single glyph:
```xml
<g id="r1" class="rest">
  <use xlink:href="#E4E5-..." />
</g>
```

### stroke-based (requires CSS override)

**hairpin** — Wedge polyline:
```xml
<g id="hp1" class="hairpin">
  <polyline fill="none" points="..." />   <!-- fill="none" inline -->
</g>
```

CSS rules (existing in ScorePreview.tsx):
```css
.score-hover.hairpin * { fill: none !important; stroke: rgba(59, 130, 246, 0.5) !important; }
.score-active.hairpin * { fill: none !important; stroke: rgba(59, 130, 246, 0.85) !important; }
```

### mixed (fill + stroke children)

**octave** — Glyph + dashed line + hook:
```xml
<g id="oct1" class="octave">
  <use xlink:href="#E510-..." />                  <!-- "8va" glyph (fill) -->
  <path d="..." stroke-dasharray="36 72" />       <!-- dashed line (stroke) -->
  <polyline fill="none" points="..." />           <!-- hook (stroke) -->
</g>
```

CSS rules (existing in ScorePreview.tsx):
```css
.score-hover.octave > path,
.score-hover.octave > polyline { fill: none !important; stroke: rgba(59, 130, 246, 0.5) !important; }
.score-active.octave > path,
.score-active.octave > polyline { fill: none !important; stroke: rgba(59, 130, 246, 0.85) !important; }
```

**pedal** — Glyph + bracket line/hook (bracket style):
```xml
<g id="p1" class="pedal">
  <use xlink:href="#E650-..." />                  <!-- "Ped" glyph (fill) -->
  <path d="..." />                                <!-- bracket line (stroke?) -->
  <polyline fill="none" points="..." />           <!-- hook (stroke?) -->
</g>
```
> **Not yet verified.** Currently works with default fill rules only. Bracket-style pedal markings may require mixed strategy similar to octave.

### overlay (JS-generated)

**measure** — Semi-transparent rect:
- No CSS class-based highlight
- JS dynamically creates an SVG `<rect>` covering the staff area
- Rect is inserted as first child of the measure `<g>` (renders below notes)
- Opacity: 0.06 (hover), 0.12 (active)

## SVG Inspection Cheatsheet

### Finding an element in DevTools

1. Right-click the element in the rendered score → Inspect
2. Look for the `<g>` with matching `class` attribute
3. Check the `id` attribute — it matches the MEI `xml:id`

### Checking fill/stroke behavior

1. Expand the `<g>` to see child elements
2. For each child, check:
   - Does it have inline `fill="none"`? → Needs stroke override
   - Does it use `<use>` or `<text>`? → Fill-based
   - Does it use `<path>` or `<polyline>` without `fill="none"`? → Fill-based (path used as filled shape)

### Quick test for highlight correctness

1. In DevTools, add class `score-hover` to the element's `<g>`
2. Check:
   - Are all parts highlighted? (no missing children)
   - Are any parts incorrectly filled? (stroke elements getting unwanted interior fill)
   - Is the drop-shadow visible?
3. If interior fill appears on lines → needs stroke or mixed strategy
